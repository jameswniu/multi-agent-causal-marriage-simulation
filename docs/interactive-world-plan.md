# LoveWorld interactive world plan

Build the interactive world in 2D: a top-down pixel town drawn with PixiJS v8 inside the existing React 18 app, with Kenney's public-domain art, replaying the logs the engine already writes, and no Blender or 3D in this phase. Put Claude Haiku 5.5 behind the public endpoint, keep Gemini 3.5 Flash-Lite on a paid key as a drop-in second adapter, and let a 50 to 100 case eval choose between them. The model only translates a visitor's words into a small typed shock spec, which the server validates against the catalog bounds, the visitor reads and edits on a card, and the engine runs as a new experiment forked from the world they were watching, so the model never runs the simulation, never touches the agents' rules or the memory treatment, and is never on the replay path. It stays safe and cheap because it is one short call with no tools, behind Cloudflare Turnstile, server-side validation and hard caps (400 characters in, 3,000 translations a day, a $50 monthly spend limit), which hold the model bill to about $43 a month at worst, on top of about $48 a month for a 4 GB Fly machine and its disk. The first milestone is a week of contract, tests and fixes to today's run endpoint, which currently lets any caller overwrite a curated experiment, override the agents' decision weights and start an engine run with no timeout, and the town itself follows in two weeks.

## The world screen

The World page is already the default route and the first item in the nav (`frontend/src/App.tsx`), so the product grows out of it rather than beside it. A visitor lands in a town that replays a finished, hashed run, and everything else (the inspector, the shock composer, a new experiment's results) opens inside that screen. The couple, agent, Overview and Comparisons pages stay as deep views one click away.

### The town

One couple is one house, and its two agents are two small figures at the house. The control and treatment arms are two districts side by side, as the grids are today, with roofs in the arm colours the dashboard already uses. Between them sits a plaza where single agents live: the divorced, those back in the remarriage market, and dating pairs. Remarriage households get a third row of houses (the "After divorce" strip the page already draws), and because a remarriage couple has no arm while each member keeps their own, its roof is split in the two members' colours. Houses sit in a fixed grid in couple id order. That order is a stable address, not a neighbourhood. The engine's only network is a Watts-Strogatz ring over agent ids (`docs/design.md`), but in the example run 487 of the 999 pairs of id-adjacent initial couples sit in different arms (measured), so no street layout can show the network honestly, and the canvas does not try.

State is shown as posture, not as a legend colour. A married couple is at home. A couple in conflict stands outside facing away under a yellow marker. A separated couple has one figure at the edge of the plaza. A divorce dims the house and sends both figures to the plaza, and a broken-up dating pair splits apart there. Every position is a pure function of the per-day `states` strings that `/api/world` already serves and of that day's state changes. Motion within a day is cosmetic interpolation between two logged days and is never stored or read back. A footnote under the canvas says so: positions are a layout, the engine has no space, and everything on screen is simulated.

One lens at a time recolours every house by one logged daily number, green to red: trust, stress, retained grudge (the saturated negative load), warmth (the positive load), satisfaction, or orphan days, the new count of days without a shared warm memory (`docs/contracts.md` section 7). The grudge lens is the treatment at town scale, with the treatment district reddening over the year. Lenses come from a small binary endpoint that serves one byte per agent per day, which for 2,000 agents over 365 days is 730,000 bytes per field by arithmetic. Full precision is fetched only for the couple being inspected.

The canvas must work from a phone to a wide monitor. At 1,000 houses on a 1,600 pixel canvas a house is 40 pixels wide (the rendering survey's arithmetic), while on a 390 pixel phone the same grid leaves under 10 pixels a house. So the town has two levels of detail: below about 24 pixels per house it draws roofs only, like today's tiles, and figures appear as the visitor zooms in (the threshold is an estimate, tuned in M1). On a phone the main view is the existing tile grid, which already meets the contract's bar of staying smooth at 50 days per second with 1,000 tiles (`docs/contracts.md` section 5), and the town opens one district at a time. `WorldGrid` also stays as the mini-map beside the town and as the fallback when WebGL is missing, keeping its keyboard picking and its screen-reader live region, which a sprite canvas cannot offer.

### Keeping the treatment in view

The first line of the page stays the framing sentence built by `framingSentence` (`frontend/src/pages/World.tsx`, line 81), for the example "On the left a fight fades from memory in 14 days. On the right it lingers for 90. Nothing else differs.", under the "Simulated evidence" banner. A "What differs" chip in the top bar uses `whatDiffers` from `frontend/src/arms.tsx`, so the one difference between the arms is on screen in every view. The inspector shows the treatment as a mechanism and the grudge lens shows it as a picture.

### The time bar

The time bar keeps everything `World.tsx` does today: play and pause, 1x, 10x and 50x days per second, the arrow keys, Home, End and space, and at most one day per rendered frame. It gains four things. A density strip under the scrubber shows conflicts started, separations and divorces per day for each arm, so the eye finds the eventful weeks. Each shock appears as a band from its start day to its last day, in the arm's colour, or neutral for a world event aimed at everyone. A "next event" button steps the selected couple to its next logged event. The day label reads as a date in the run ("Day 143, week 21"). In twins mode the count of couples whose fate differs sits beside the label, as it does today, and in a world forked from another (see the next section) the same place shows how many houses differ from the parent world that day, found by comparing the two `states` arrays the page already loads.

### The day's events as a digest

A letter per event, RimWorld style, floods at any speed. In the example run at the current commit the World ticker sees about 500 events a day once memory consolidations are left out (mean 504, median 515), and the eight kinds a severity-coloured letter stack would show come to a median of 313 a day (measured). What a viewer needs are the state changes (separations, divorces, reunions, matches, marriages and break-ups), with a median of 19 a day and a maximum of 35. So the right edge holds a per-day digest of those counts by arm, red for separations, divorces and break-ups and blue for reunions, matches and marriages, and clicking a line highlights those houses. The selected couple's own events are listed in full from the `/api/couples/{id}` payload the inspector already fetches. Memory consolidations stay out of the list, as `splitTicker` in `World.tsx` already arranges.

The digest also removes a cost the public site cannot carry. Today `useDayEvents` requests `/api/events?day=N` on every day change, so one viewer at 50x makes 50 requests a second. Each costs about 1.8 ms of handler CPU and about 5.4 ms through the whole request (measured in process), which is 90 to 270 ms of CPU per second per viewer by arithmetic, against a shared Fly vCPU's baseline of 5 ms in every 80 ms (Fly's CPU performance page). The digest is computed once per experiment and shipped with `/api/world` (six kinds, three groups and 365 days make 6,570 counts by arithmetic). Raw events are fetched only while paused, in `from` and `to` ranges under the existing 5,000-row cap.

### The inspector

Clicking a house opens a side panel (a bottom sheet on a phone) without stopping the world. For the day under the scrubber it shows the couple's arm in plain words from `arms.tsx`, its state and how long it has held, trust and affect sparklines up to that day, the day's decision with its probabilities from `probabilities()` in `frontend/src/components/UnderTheHood.tsx`, whether leaving is on the menu under the new leave gate (a closed gate logs `u_leave` as null), the orphan-day count, any sealed marriage from the new `legacies` list, and any shock that landed that day. It links to the couple and agent pages for the full history.

The centre of the panel is the memory list: each episode one partner holds about the other, with its strength that day. At the current commit that strength is `intensity * 0.5 ^ (max(0, t - day - plateau) / half_life)`, with a two-day plateau, weekly consolidation of old episodes into one standing grievance, reconciliation or positive memory, and a freeze while a couple is separated (`docs/design.md`). This list is the treatment as a mechanism, because the same fight visibly fades faster on the left than on the right. A copy of those rules in the browser is exactly where the inspector could quietly disagree with the engine, so the strengths are computed once in Python and served by `GET /api/couples/{id}/memory?day=N` (for example `/api/couples/417/memory?day=143`). A parity test gates the endpoint. Summed with the valence weights and passed through the saturation transform, its strengths must reproduce the logged `neg_a`, `neg_b`, `pos_a` and `pos_b` in `daily.parquet` on every day of three fixture couples: one that separated, one with consolidated memories and one that divorced. The example run holds 46,708 amplified and 39,223 consolidated episode rows (measured), so the test has material. If the port cannot pass, the panel shows the logged loads and the episode list without per-episode strengths rather than numbers that disagree with the log.

A speech bubble appears only above the selected couple and carries the chosen action as a word ("repairs", "withdraws"). Probabilities stay in the panel. On day 200 of the example 229 treatment couples are in conflict (the README's capture, matched by measurement), so a bubble over every figure would be noise. A twin toggle shows the couple's fate under the other arm from `/api/twins/couples/{id}` when a twins run exists, which is true for curated experiments. Worlds made by visitors have no twins run, so the toggle is hidden there with a one-line reason. There is no box for interviewing an agent. Explanations are templated from the logged utilities, because the baseline has no LLM agents.

### Why 2D, and the exact stack

The town is 2D and top down, drawn with PixiJS v8 (8.22.0, MIT) mounted as a plain `pixi.js` Application inside a `useEffect`, the way `WorldGrid.tsx` already owns its canvas. React stays at 18.3.1. `@pixi/react` is not used, because version 8.0.5 requires React 19 (rendering survey). The art is Kenney's public-domain packs, Tiny Town (16 by 16 pixel tiles, 130 files) and Roguelike Characters (450 files), which need no attribution (rendering survey, from Kenney's support page). Whether those characters have the facing and walking frames the posture rules want is unverified and is checked in M0. If they do not, posture is carried by position and a small marker.

The reason is the data. The engine has no spatial model, so a 3D scene adds depth and camera work without adding information, while the logs carry exactly what 2D shows: where an agent is relative to home, a posture, and one colour per lens. If "Minecraft-like" means the blocky pixel look, the town has it. If it means a voxel world with a free camera, nothing in the logs fills it. The table compares the options the rendering survey weighed.

| Option | Budget for 2,000 moving figures | Fit with React 18 | Art and licence | Effort to first playable | What it blocks later |
|---|---|---|---|---|---|
| PixiJS v8, plain Application (chosen) | Bunnymark: 100k sprites at about 15 ms CPU and 2 ms GPU per frame, hardware unstated | Mounted in a useEffect, as WorldGrid owns its canvas | Kenney CC0 Tiny Town and Roguelike Characters | Smallest, about two weeks (survey estimate) | No camera into a room, so scenes become 2D cutscenes or video |
| Phaser 4 | SpriteGPULayer, "a million or more" (vendor claim) | A second game loop and input system, bridged by an EventBus | The same CC0 packs, Tiled import | Small, plus the two-loop bridge | The same scene limits as PixiJS |
| Three.js through React Three Fiber | InstancedMesh, draw calls kept under 1,000 (R3F guide) | R3F 8.18.0 runs on React 18, 9.8.1 needs React 19 | Kenney 3D kits (CC0), Blender glTF, Mixamo baked into the build | Medium to large: lighting, camera, animation | Little, though animated instanced characters are custom work (unmeasured) |
| Bevy 0.20 compiled to WebAssembly | Unmeasured, WebGL2 by default, WebGPU experimental | Canvas plus wasm-bindgen, with the UI bridged or duplicated | GlTF through Bevy's loaders | Largest: a renderer from scratch in Rust | Downloads of 4.8 to 13 MB in a 2022 example, and no governance gain |
| Existing WorldGrid canvas | Meets the contract at 1,000 tiles, 2,000 animated figures unmeasured | Already integrated | Hand-drawn sprites | Small at first, growing with each feature | Rebuilds what PixiJS ships, with no path to a scene stage |

Phaser would also work, but it brings a second game loop and input system beside React for no capability the town needs. Godot's web export is out because the page "cannot easily" drive the game from outside, so the scrubber and forms would be built twice, and Bevy in the browser buys nothing the server does not already give, since the simulation must stay where the manifest is written (rendering survey). Blender gets a defined later home rather than a no: a lazily loaded React Three Fiber scene stage for the roadmap's Phase 2 scenes, timed with the React 19 upgrade that R3F 9.8.1 and `@pixi/react` both need, using Kenney Mini Characters (25 animated files, CC0) or Mixamo characters baked into the build, since Mixamo's FAQ is silent on redistributing raw files. The town stays the map in that future too.

One decision gate guards the choice. M0 measures frame time at 50 days per second with 2,000 animated figures on a laptop and on a mid-range phone, PixiJS against the existing canvas. If PixiJS misses the contract's smoothness bar, the figures move onto the existing canvas and the rest of this plan stands, because the data model does not depend on the renderer.

## The natural-language shock pipeline

### From words to a run

1. The visitor opens the composer from the time bar ("Add shock"), from a right-click on a district ("Shock this arm") or on the plaza ("Shock everyone"), or by typing into the line docked under the scrubber, "Describe something that happens to them...", with the eight catalog kinds as chips beside it. In this phase a shock hits a whole arm or everyone. A click on one house opens the inspector, because the spec has no couple target and a shock on one couple is a story, not an experiment.
2. The browser sends `POST /api/shocks/translate` with the text (at most 400 characters), a fresh Turnstile token, and the context: the parent experiment, its number of days, the scrubber day as the default start and the clicked arm as the default target. The request passes through the Cloudflare Worker described under the public endpoint.
3. The API checks its exact counters, then looks for a cached translation of the same request.
4. On a miss it calls the model with one frozen system prompt (`shock-translate-1`) and the `shock-spec-1` JSON schema. The visitor's text sits in the user turn inside a delimited block. The model has no tools, no retrieval and no memory across visitors, and nothing one visitor wrote is ever shown to the model on another's behalf.
5. The API parses and validates the output, stores a translation row, and returns a `translation_id`, the spec, any rejections and the model's notes.
6. The browser shows the shock card. The visitor reads it in plain words, edits any field, and sees the shock's days and the targeted district drawn as a ghost overlay on the time bar and the town.
7. "Run as a new experiment" sends `POST /api/experiments/{parent}/fork` (for example `/api/experiments/example/fork`) with the `translation_id` and the edited shocks. The model is not called again. The server copies the parent's effective config, appends the shocks, stamps provenance and queues a job. The page shows the queue position, then the world as soon as the engine finishes, then the statistics when the analysis attaches.
8. The new world opens with its provenance on the experiment card and the parent comparison on the time bar. Replaying it never involves the model.

### The typed spec

`shock-spec-1` maps one to one onto the shock entry that the run endpoint, `parse_shock` in `python/loveworld/experiment.py` and `frontend/src/validation.ts` already accept, so the translator ships with no change to what the engine runs.

```json
{
  "schema_version": "shock-spec-1",
  "target": "treatment",
  "kind": "job_loss",
  "member": "random",
  "trait": null,
  "start_day": 60,
  "end_day": 180,
  "magnitude": 1.5,
  "notes_for_user": "Read as a job loss for one partner on day 60, with extra daily stress for four months.",
  "assumptions": ["You said one of them, so the engine picks a partner at random in each couple."],
  "unsupported": ["Money is not modelled here, so the loss is expressed as stress."]
}
```

`kind` is one of the eight catalog kinds (`job_loss`, `financial_crisis`, `temptation`, `intimacy_mismatch`, `trait_shift`, `daily_texts`, `anniversary`, `date_nights`). `target` is `treatment`, which makes the shock part of the intervention, or `all`, a world event under which the memory treatment is tested. `member` is `a`, `b` or `random`. `trait` is one of the nine shiftable traits and appears only with `trait_shift`. `start_day` and `end_day` are whole days inside the run, with a null `end_day` meaning the catalog default. `magnitude` lies inside the kind's catalog range, for example 0 to 5 units of stress for a job loss (`SHOCK_CATALOG` in `python/loveworld/schema.py`, pinned to the engine's `shock-catalog` output by the existing `test_python_catalog_matches_engine_catalog`). The last three fields are for the author only: `notes_for_user` holds at most 200 characters, and `assumptions` and `unsupported` at most three short items each. Nothing in the spec can name a memory half-life, a memory rule, the leave gate, a legacy setting, a policy weight, the softmax temperature, assignment, seeds or analysis settings.

`shock-spec-2` (milestone M3, behind an explicit cut line) adds one `custom` kind whose `effects` list holds one to four primitives, each on a different channel, for example `{"channel": "stress_daily", "member": "both", "start_day": 90, "end_day": 210, "cadence": "daily", "magnitude": 0.6}`. The channels are the ones the eight kinds already use, and each bound is the largest value a preset reaches at that cadence: a stress jump of 0 to 5 once, extra stress of 0 to 1.5 a day (the financial crisis maximum, 0.3 times 5), an outside-encounter probability of 0 to 1, a trait shift of minus 1 to 1, a positive episode of up to 0.25 a day, 0.3 a week, or 1.0 once or yearly (daily texts, date nights and the anniversary at their maxima), a trust rise of up to 0.04 once or yearly, and an affect lift of up to 0.1 a day (from the formulas in `docs/contracts.md` section 6 and the ranges in `ShockKind::bounds` in `engine/src/config.rs`). Bounds per cadence close the loophole of a daily effect at a yearly preset's size, and one primitive per channel stops stacking inside a shock, so a custom shock can deliver no more over any span than the strongest preset of the same cadence. The label that names a custom shock in the tables is built by the server from its first channel and start day, for example `stress-daily-d90`, so no free text written by the model or by a visitor ever reaches the tables, the manifest or another visitor's screen. Each manifest's provenance names exactly one spec version.

### Validation

The model's output is untrusted until it passes the validator the run endpoint already uses. `loveworld/translate.py` treats a refusal or a `max_tokens` stop as a failed translation, never as a spec, then parses the JSON and hands each shock to `parse_shock`, extended for the spec's extra fields. The validator rejects unknown keys, enum values in any other spelling or casing, days outside the run, an `end_day` before its `start_day`, a magnitude outside the catalog range, a trait on any kind but `trait_shift`, and free text over its length or outside a plain character set. It rejects rather than clamps, and the card lists each rejection where `validateRun` errors appear today. Both vendors say to validate values in the application whatever the schema says: Claude's structured outputs accept no numeric `minimum` or `maximum` and no string length limits (the claude-api reference), and Gemini's documentation warns that output can be "schema-compliant but semantically incorrect" (rendering survey).

The engine validates a third time, which today it does not fully do. `SimConfig` and `ShockConfig` derive serde without `deny_unknown_fields`, and a run whose shock says `"magnitud": 5.0` exits 0 and applies the default of 1.5 (measured at the current commit). M0 adds `deny_unknown_fields` to every engine config struct, after checking that every committed manifest and experiment file still parses, so a misspelt or extra field fails the run even if Python is bypassed. In M3 the custom kind's bounds live in one Rust table, printed by a new `effect-catalog` subcommand, enforced when the engine loads its config, and mirrored in Python under the same parity test pattern the shock catalog already has.

### The shock card

The card has two columns. The left one states the spec in plain words, written by a new `shockSentence` function from the structured fields and never by the model, so the words always match what will run. Today's `shockWords` cannot do this job: it prints the catalog blurb and the start day and leaves out the magnitude, the end day, the partner and the target, so a job loss of 0.1 reads the same as one of 5.0. A test feeds the renderer every field of the spec and fails if any value, with its unit, is missing from the sentence. The right column states the spec in engine terms, from templates that mirror the update rules and clamps in `engine/src/systems.rs` and are pinned by a test to the engine's default config. For a job loss of 1.5 from day 60 to day 180 it reads: on day 60 partner a's stress jumps by 1.5, with stress capped at 3, and until day 180 they carry 0.15 extra stress a day, which with the daily decay of 0.7 settles about 0.5 above where it would otherwise be (0.15 divided by 0.3, by arithmetic from `stress_decay` in `config.rs`).

Below the columns sit the model's reading, labelled as the model's, its assumptions and anything it could not map. The card says whether the shock hits only the treatment arm, and so is part of the intervention, or everyone. Every field is editable with the widgets `NewExperiment.tsx` already uses. A separate slider, which the model can never fill, sets the treatment arm's memory half-life within the form's existing 1 to 3,650 day range, so a visitor can run a memory experiment by hand while the translator stays away from the treatment. Two buttons close the card: "Run as a new experiment" and "Discard".

### Forking, provenance and replay

A visitor's run must be a variation of the world they were watching. Reusing `buildRequest` from `NewExperiment.tsx` would not give that: it sends no seeds, no control overrides and no engine overrides and fixes the resamples at 500, so a shock composed while watching `contagion-block` would silently drop its block assignment and network terms. The fork endpoint copies the parent's effective config from its `config.json` and allows exactly three changes: appended shocks, the treatment half-life from the slider, and the provenance block. A test asserts that the child's config equals the parent's apart from those keys and the name.

Comparing a child with its parent on the same seeds only works if a shock that does nothing changes nothing, and today it does not. `shock_system` in `engine/src/systems.rs` draws a random partner from the couple's main random stream on the shock's start day, so every later draw for that couple shifts. In a run of 400 couples over 180 days, a job loss of magnitude 0 aimed at a random partner from day 60 changed 34,201 couple-days, all on or after day 60, and left 24 couples in a different final state, while the same shock aimed at partner a changed nothing (measured). M2 moves these draws to a dedicated keyed stream (the dynamics seed, a `shock_member` domain, the shock's index and the couple id), with a test that a zero-magnitude shock leaves `daily.parquet` byte-identical. The change moves the hashes of the four experiment files that carry shocks, all of which draw a random partner, so it ships as a new engine version, those four are re-run, and old manifests replay against the build that wrote them. The example run has no shocks and keeps its hash.

Provenance is stamped by the server and never accepted from the browser, which sends only the `translation_id`. The server looks up its translation row (a keyed HMAC of the text, the model id, the prompt and schema versions, the hash of the raw output and the validated spec), computes `edited` by comparing the submitted shocks with the stored spec, adds the parent's name and determinism hash, and signs the block with an HMAC key held as a Fly secret. The engine gains an optional `provenance` object in `SimConfig` that no system reads, `config.json` and the manifest echo it, and the manifest gains a `provenance_sha256`. Today a top-level `provenance` key is silently dropped from both files (measured), so this is a small M2 engine change, shipped reader first: the engine and Python accept the optional key before the translate endpoint emits it, and every existing manifest stays valid. `parse_experiment` refuses `engine.provenance` beside `engine.shocks` and `engine.memory`, and `analysis.write_summary` receives provenance explicitly and copies it into `summary.experiment`. The Overview and the experiment list show "translated from text, edited by the visitor" with the model id and short hashes beside the determinism hash they already show.

Replay reads the manifest's config and runs the shocks in it. It never sees the text and never calls a model, and a test asserts that two runs differing only in provenance give identical table hashes, since the determinism hash covers the tables alone. Bit-exact replay is promised only on the same platform and toolchain (`docs/design.md`), while `rust-toolchain.toml` pins only `stable` and the engine calls `powf` and `exp`. So M0 pins an exact toolchain (the installed one is 1.99.0) and records a build id in the manifest, and the nightly replay of a sample of public runs compares only runs from the same build.

### The eval that picks the model

Before launch both adapters run over the same 50 to 100 descriptions with expected specs (both surveys). The set holds plain cases, near misses that must map to the closest kind with an `unsupported` note, and hostile lines: "make the treatment arm forget faster" must come back unsupported because memory is the treatment, "ruin everyone" must map to nothing, and prompt-injection text must yield either an ordinary valid spec or a failure. Refusals and truncations count as failures. The eval records p50 and p95 latency, which is unmeasured for both models today, and once M3 lands it runs every custom spec through the engine to flag degenerate worlds, such as a treatment-arm divorce share above a set threshold within a week. A larger model may grade the set offline, never on the public path. Accuracy is unmeasured until the eval runs, and the validator and the card keep the choice low stakes.

## The public endpoint

### The model

Claude Haiku 5.5 (`claude-haiku-5-5`) is the default. The call sets `output_config.format` to the `shock-spec-1` JSON schema, turns thinking off with `thinking: {"type": "disabled"}` at effort `low`, and caps `max_tokens` at 400. Thinking is on by default for this model and counts toward `max_tokens`, so leaving it on could spend the cap and return a cut-off spec, and disabled thinking is accepted at effort `high` or below (claude-api reference). Prices are $0.10 per million input tokens and $0.50 per million output tokens for prompts up to 100,000 tokens, cache reads cost a tenth of the input price and five-minute cache writes 1.25 times it, the minimum cacheable prefix is 512 tokens, and a new schema is compiled once and then cached for 24 hours (claude-api reference). Haiku 5.5 rejects non-default sampling parameters, so the temperature cannot be pinned to 0 and two calls on the same words can differ. That is acceptable because the validated spec, not the text, is the experiment's input, and repeated requests are served from the translation cache. Anthropic's API data is not used for training by default, and a spend limit set in the Console is a hard stop that returns HTTP 400 once reached (llm_endpoint survey).

Gemini 3.5 Flash-Lite on a paid key is the second adapter behind the same four-line interface (prompt, schema and text in, JSON out) in `loveworld/translate.py`, because James asked about Gemini and it is a stable model with structured output. It costs $0.30 per million input tokens and $2.50 per million output tokens, thinking included (Google's pricing page). Its thinking runs at the `minimal` level by default with no off setting, `max_output_tokens` counts thinking, and a response cut off while thinking still bills the thinking (Google's thinking page), so its adapter gets its own output cap, set from the eval, and every truncation counts as an eval failure. The free tier is excluded because Google uses its content to improve its products, which the paid tier does not (pricing page). Gemini 3.1 Flash-Lite is cheaper but has an earliest shutdown date of May 7, 2027, and Google limits Gemini 2.5 Flash-Lite to accounts that already used it (llm_endpoint survey). At the survey's assumed 2,000 input and 250 output tokens, a translation costs about $0.33 per 1,000 on Haiku 5.5 without caching and about $1.23 per 1,000 on Gemini 3.5 Flash-Lite before thinking tokens. If James prefers a single vendor, Gemini on a paid key is acceptable, since the server-side validator, not the model, is the gate.

### Hosting and keys

The FastAPI app and the engine run on one Fly.io machine in Ashburn with a dedicated CPU and 4 GB of memory. A performance-1x machine with 2 GB is listed at $33.00 a month and extra memory at $6.00 per GB a month, so 4 GB comes to $45.00 a month by arithmetic, and a 20 GB volume for results adds $3.00 at $0.15 per GB (Fly's pricing page, read 2026-10-11). Shared CPUs are the wrong fit. A shared vCPU's baseline is 5 ms in every 80 ms, with a burst balance that starts at 5 seconds and caps at 500 (Fly's CPU performance page), while one run of 1,000 couples for 365 days takes about 1.0 second of engine CPU, and the engine plus the analysis took 1.7 to 1.9 seconds end to end at the dashboard's 500 resamples and 2.3 seconds at the full 2,000 (measured on the development laptop). Throughput on the real host is unmeasured, and M4 measures runs per hour there before the run caps below are fixed.

Memory sizing comes from measurement. The engine peaked at about 0.52 GB for 1,000 couples over 365 days and at about 1.87 GB at the 2,000 by 730 cap. The API process started at 119 MB, grew to 576 MB after one run because the analysis runs inside it, and reached 1.8 GB after three runs and three loaded experiments, because `ExperimentStore.loaded` keeps every experiment ever viewed and drops one only when it is re-run. Each warmed-up load added 0.3 to 0.4 GB. These are macOS figures, and Linux figures are unmeasured until M0. Three changes bound the footprint: public runs are fixed at 1,000 couples for 365 days, the engine and the analysis run in a separate worker process so the API never holds analysis tables, and the store keeps at most two loaded experiments and rebuilds an evicted one from disk (0.55 to 0.73 seconds measured). Render's free tier is dropped because its filesystem is ephemeral (review finding), so runs and counters would vanish, though it could still serve a read-only demo from fixtures.

Every secret lives as a Fly secret and nowhere else: the provider key (one per environment, in a dedicated workspace or project so its spend limit stands alone), the HMAC key for text hashes and provenance, and the shared secret that the Cloudflare Worker adds to each request it forwards. The Vite bundle never sees any of them, and the browser talks only to `/api` routes through Cloudflare. Any suspicion of a leak means rotation.

Cloudflare's free plan sits in front, and the Worker is mandatory. It verifies the Turnstile token at `siteverify` (a token is valid for 300 seconds and can be validated once, so every translate call needs a fresh one), applies per-session and per-IP limits, and forwards with the shared-secret header. The origin rejects any request without that header, so the `fly.dev` address cannot be used to go around the edge, and it trusts `CF-Connecting-IP` only on requests that carry the secret. Per-IP limits key IPv6 addresses on their /64 prefix. The free plan's one WAF rate-limiting rule (IP only, 10-second period) stays as the burst stop on the translate and fork routes, and Workers Free allows 100,000 requests a day (llm_endpoint survey).

### Abuse and cost caps

Every cap here is a pace we chose, not a limit any platform imposes. A translate call takes at most 400 characters and gets at most 400 output tokens. Each IP or /64 gets 5 translations a minute and 60 a day, each anonymous session 30 a day with one in flight, and the whole service 3,000 a day, released in hourly slices of 125 so that a flood spends at most one hour's allowance. A script can drop its cookie, so session counters alone mean little: the per-IP counters carry fairness and the global counter carries the bill. Identical requests are answered from the cache, keyed by a keyed HMAC of the whole user turn (text, days, default start and target) together with the prompt version, schema version and model id, so a changed prompt never serves an old translation. Everything derived from a visitor's text, cached specs and the model's notes included, is deleted after 24 hours.

Runs cost CPU and disk rather than tokens. Each IP gets one run every two minutes and ten a day, and the service 100 a day, with one engine job at a time and a queue of five whose position the page shows. A sixth caller gets a plain message that the world is busy, not an error. The engine subprocess gets a 60-second timeout, about fifty times the measured run and to be reset from the host measurement, because `engine.py` calls `subprocess.run` with none today. A public experiment carries at most four shocks. Anonymous results are deleted after 24 hours, while curated experiments are read-only and exempt from that sweep. One run writes 56 MB (measured), so 100 runs a day keep at most 5.6 GB of visitor results by arithmetic, and a disk ceiling refuses new runs at 15 GB used, leaving the rest of the volume for curated experiments.

At those caps the model bill is bounded by arithmetic from the listed prices. On Haiku 5.5, 3,000 translations a day at the ceiling of 2,200 input and 400 output tokens cost $1.26 a day without caching, about $39 a month (the survey's figure), or $1.40 a day, about $43 a month, if every call writes the prompt cache. Caching the frozen prefix pays off only above a hit rate of about 22 percent, so it is switched on once the measured hit rate clears that. The Console spend limit is set at $50 a month behind the counters. On Gemini 3.5 Flash-Lite the same traffic costs $4.98 a day before thinking tokens (survey), or $9.48 a day if each call used a 1,000-token output cap in full. There the hard stop is a prepaid balance on a dedicated billing account, because a balance at zero stops every project linked to it, and Tier 1 adds a rolling spend limit of $10 per ten minutes (review findings). With hosting, the worst month at full caps on Haiku is about $91 ($45 machine, $3 volume, $43 model), and an ordinary month is about $48 plus $0.33 per 1,000 translations.

### What an attacker can still do

The structure carries most of the safety. The model has no tools and no agency, and its output is a bounded spec that the server re-validates and a person reads before anything runs, which answers OWASP's improper output handling and excessive agency risks (LLM05 and LLM06, interaction survey). The system prompt holds no secrets, so prompt leakage (LLM07) has nothing to leak. The worst a successful prompt injection (LLM01) can do is produce a wrong but valid spec that its author sees before Run, that is logged and hashed, and that describes a world labelled simulated. No free text written by the model or a visitor reaches another visitor. The raw prompt is never displayed or stored beyond the request, the model's notes are shown only to the author, experiment names are assigned by the server (for example `nl-7f3a2c-1`) with no overwrite, and the experiment list shows the curated experiments plus the visitor's own, while a shared `?experiment=` link still opens for anyone who has it. Short prompts hashed without a key could be reversed with a dictionary, so the stored hash is a keyed HMAC, and the page states the 24-hour retention in one sentence. What remains is availability: solved Turnstile challenges and rotating addresses can spend the global allowance, the hourly slices limit that to an hour at a time, and curated worlds keep working without the translator. Unbounded consumption (LLM10) is held by the caps above.

## Engine, API and frontend changes

### The gates, as tests

Six tests land in M0, before any feature, together with a new section 8 of `docs/contracts.md` covering the translate endpoint, both spec versions, the fork and job routes, provenance, the lens fields, the digest, the memory endpoint and public mode. The contract changes before any consumer, as its first paragraph requires.

1. The engine cannot call a model. `Cargo.lock` lists no `reqwest`, `hyper`, `ureq` or `isahc`, `engine/src` uses no `std::net` or `process::Command` (none of either today), and CI runs `loveworld-engine replay` inside a container with networking disabled (Docker's `none` network).
2. The run path imports no model SDK. A fresh interpreter imports `loveworld.runner`, `loveworld.experiment`, `loveworld.engine` and `loveworld.analysis` and finds no `anthropic`, `google.genai` or `openai` in `sys.modules`. The translator lives in `loveworld/translate.py`, which none of them imports.
3. The spec cannot name the treatment or the rules. A walk of both spec schemas against the engine's `default-config` output finds no reachable key under `memory`, `memory_rules`, `association`, `legacy`, `policy`, `dynamics`, `market`, `population`, `assignment`, `seeds` or `analysis`, and no custom channel shares a name with any of those parameters. It follows `policy_sources_never_mention_the_arm` in `engine/tests/cli.rs` and `test_policy_and_dynamics_never_see_the_arm` in `python/tests/test_governance.py`.
4. Provenance is inert. No engine system reads it, and two runs that differ only in provenance give identical table hashes.
5. Public art is CC0 only. `frontend/public/assets/LICENSES.md` names every pack, and a Vitest test fails on any asset whose pack is not listed. LPC sprites, which mix CC0, CC-BY, CC-BY-SA, OGA-BY and GPL (rendering survey), stay out.
6. The inspector matches the log, through the memory parity test described under the inspector.

The README's governance table gains two rows, "The LLM translates, it never simulates" and "The shock vocabulary cannot name the treatment or the rules", each pointing at its test. The row "No LLM agents before the baseline passes" stays, with one added sentence: the translator is a compiler that runs before the simulation, not an agent inside it.

### Rust engine

In M0 every config struct gets `deny_unknown_fields`, the toolchain is pinned to an exact version, and the manifest records a build id. In M2 shock members come from the dedicated keyed stream, released as a new engine version with the four shock experiments re-run, and `SimConfig` gains the optional, unread `provenance` object while the manifest gains `provenance_sha256`. In M3, behind the cut line, a `custom` kind joins the eight native kinds, which stay exactly as they are so every existing manifest still replays. One generic arm of `shock_system` executes its effects and logs them the way shocks are logged today: one `interventions.parquet` row per agent and primitive with a parameter such as `custom:stress-daily-d90:stress_daily`, a `shock_custom` event per application, episode source `shock:custom:stress-daily-d90`, and partners drawn from the M2 stream. Because `engine/src/log.rs` holds `kind`, `parameter` and `source` as `&'static str`, those fields become owned or interned strings, at a cost measured in M3. Before that change, small fixture configs for all eight kinds, with a fixed and a random partner and both targets, have their table hashes recorded on the M2 engine, and the M3 engine must reproduce them byte for byte. Experiment files exist for only four kinds today (job loss, financial crisis, daily texts and trait shift), so the fixtures cover the other four.

### Python API

In M0 `engine.py` gets its subprocess timeout, `ExperimentStore` becomes an LRU of two loaded experiments, and a public mode (`LOVEWORLD_PUBLIC=1`) switches `/api/experiments/run` off and serves curated experiments read-only, leaving the local dashboard unchanged. Today that route accepts `overwrite: true` for any safe name, so a caller can replace `results/example`, and it passes `engine` overrides of policy weights, dynamics and market rates that the engine checks only to plus or minus 10,000 (`check_bounded` in `engine/src/config.rs`). In M1 `/api/world` gains the digest, `GET /api/world/fields?field=neg&member=a` returns the quantized lens bytes with their scale in a header, and the memory endpoint lands with its parity test. In M2 come `/api/shocks/translate` with both adapters, SQLite tables beside the results for translations, counters and jobs, `POST /api/experiments/{parent}/fork`, `GET /api/jobs/{id}` (queued with a position, world ready, statistics ready, or failed with a reason), the worker process, a signed session cookie, the session-scoped experiment list, the 24-hour sweeper, the disk ceiling and the nightly replay sample. Tests follow `python/tests/test_api.py`: validation and caps on translate, provenance round trip and tampering (a provenance field sent by the browser is ignored), fork equality, public mode refusing `overwrite`, `engine`, `control`, `seeds` and visitor names, the refusal at a sixth queued run, and a sweep that spares curated experiments.

### React app

In M1 a `WorldCanvas` component owns the PixiJS Application: atlases, the district layout, positions as a pure function of `states` and the day's changes, lenses, pan and zoom, picking and the two levels of detail. `TimeBar` extends today's controls with the density strip, shock bands, the next-event button and the parent comparison, `DigestPanel` replaces the ticker, `Inspector` opens beside the town, and `WorldGrid` stays as mini-map and fallback. In M2 the `Composer` and `ShockCard` arrive (with `shockSentence`, the engine-terms column, the labelled model notes, the half-life slider and the ghost overlay), along with job progress and provenance on the Overview and the experiment list. `api.ts` gains `translateShock`, `forkExperiment`, `getJob`, `getWorldField` and `getCoupleMemory`, and `types.ts` mirrors contract section 8. ## Milestones

The durations are estimates, except M1's two weeks, which is the rendering survey's estimate for a first playable. The sum is about eight to ten weeks for one engineer, or six to eight without M3.

M0, contract, gates, fixes and measurements, about one week. Contract section 8, the six gates, `deny_unknown_fields`, the toolchain pin and build id, the engine timeout, the store LRU and the public-mode switch. Measurements that must precede commitments: frame time at 50x with 2,000 figures on a laptop and a mid-range phone, PixiJS against the existing canvas; server CPU with several viewers; API and worker memory on Linux; token counts of the real prompt; and the Kenney frames check. It ends when the tests are green and the renderer is chosen from the frame-time number.

M1, the town, about two weeks. The canvas, lenses, levels of detail and phone layout, the digest, the time bar additions, the footnote, the mini-map, and the inspector with its memory endpoint. No engine change. It ends when the town is smooth at 50x on the M0 devices and the parity test passes.

M2, composer, translator and fork, on staging only, about two to three weeks. Readers ship before writers: first the engine and Python accept optional provenance and the new member stream lands as a new engine version, then the fork endpoint, jobs, worker, session list and sweeper, then translate with both adapters, counters, cache and Turnstile, and last the card. It ends when a translated and edited shock runs as a forked world whose provenance verifies and whose replay passes, and when a zero-magnitude fork leaves `daily.parquet` identical to its parent.

M3, the custom kind, about two weeks, behind the cut line. `shock-spec-2`, the effect catalog and its parity test, the per-cadence bounds, owned log strings and the hash-pinned fixtures for all eight kinds. If it slips, launch goes ahead with `shock-spec-1`, which already gives natural language over the eight kinds.

M4, public launch, about one to two weeks. The Fly machine and volume, the Cloudflare Worker and WAF rule, secrets and spend limits, a measurement of runs per hour on the host that sets the run caps, the Linux memory check, the eval over both adapters and the vendor choice, the nightly replay sample, and a load check that a full queue yields the busy message rather than errors. The translator is public only from here.

## Out of scope

A 3D or voxel world, a free camera, Blender or glTF assets, Godot or Bevy in the browser, and a browser build of the simulation. LLM agents or learned policies (roadmap Phase 3) and LLM-written dialogue, voice or avatar scenes (Phase 2). Any spec field for memory half-lives, memory rules, the leave gate, legacies, policy weights, the temperature, assignment, seeds or analysis settings. Shocks aimed at one couple or at a sampled share of an arm, which add engine targets for stories rather than experiments. An interview box or any model-written explanation in the baseline world. Showing one visitor's words to another, accounts, and keeping anonymous results past 24 hours. A third model vendor. Native mobile apps. Calibration against human data or any claim about human couples.

## Risks and open questions

Translator accuracy, the latency of both models and real token counts are unmeasured until M0 and the eval. A wrong translation is visible on the card before anything runs, and the vendor is a config value.

Frame time with 2,000 animated figures at 50x is unmeasured, and so is whether Kenney's characters have the frames the postures want. The M0 gate falls back to the existing canvas and to position-only postures.

Without a GPU the town replays slower than it did before the lenses landed. Measured in Chrome's software renderer (SwiftShader) at 50 days a second, the World page played about 31 frames a second at 1440 by 900 before the lenses build, fell to about 8 after it, and is back to about 20 now. Each day's changing numbers had made the browser redraw the density strip's thousands of bars, so the strip now sits on its own layer with its cursor beside it. At 1800 by 1000 the page plays about 21 frames a second against 23 to 26 before. The remaining gap is the daily redraw of the numbers themselves, so a visitor without a GPU gets a usable but slower replay. These figures come from a busy laptop.

Memory and CPU on the real host are unmeasured. The figures here come from macOS on a busy laptop, so M0 and M4 re-measure on Linux and on the Fly machine before the caps are fixed. The engine run, not the token bill, is the real denial-of-service surface, which is why runs get their own queue, pace and disk ceiling.

The member-stream fix and the toolchain pin move existing hashes. Both ship as versioned changes, with old manifests replayed against the build that wrote them.

The engine is moving. The memory rules, leave gate and legacies landed on 2026-10-11 (commit 50a6a0f), and the run times measured here differ from the README's "about ten seconds". Contract section 8 and the gates keep this plan honest as the engine changes, and its citations should be re-checked at each milestone.

Visitors may read figure positions as evidence. The footnote, the layout-only rule and never storing positions keep the renderer out of the causal path.

Provider churn is real (Gemini 3.1 Flash-Lite's earliest shutdown is May 7, 2027). Replay never calls a model and provenance stores the model id, so old runs stay legible and replayable whatever happens to a vendor.

The novelty claim is narrowed. No system in the interaction survey shows a deterministic, editable, replayable spec before an event lands, but ChatScene (CVPR 2024) turns text into domain-specific code run in a driving simulator, so the claim holds for agent worlds and games only.

Open questions for James, each with the default this plan assumes. Whether one vendor is enough: the default is Haiku 5.5 with the Gemini adapter kept warm, decided by the eval. Whether visitors may change the memory half-life by hand: the default is yes, by slider, never by text. Whether visitor worlds get twins: the default is no, because a twins pair cost 2.8 seconds and 111 MB more here (measured). Whether launch opens the translator to everyone at once: the default is the full caps above from M4, with the global allowance as the dial if traffic surprises.
